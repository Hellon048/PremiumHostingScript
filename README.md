# remnawave-deploy

Один скрипт, две роли: **RU-вход** каскада Remnawave (белый IP, self-steal
или SNI из белого списка) и **EU-выход** (self-steal + Cloudflare WARP,
либо просто DIRECT). Поднимает сервер с нуля одной командой — без ручной
возни с Docker, Reality-ключами, WARP-регистрацией и Config Profile.

```
Клиент → TCP/443 → [RU-нода] ──RU-сайты/IP──► напрямую
                        │
                        └──остальное──► [EU-нода] → WARP (или DIRECT) → интернет
```

## Состав репозитория

| Файл | Что делает |
|---|---|
| `scripts/install-remnawave.sh` | Ставит RU-вход или EU-выход — выбор роли в начале (`ROLE=ru` / `ROLE=eu`) |

## Что подготовить ДО запуска скрипта

Не пропускайте этот раздел — без части этого скрипт либо не запустится,
либо застрянет на середине.

### Для обеих ролей

- **Сервер:** чистый Debian/Ubuntu VPS с root-доступом по SSH.
- **Свободные порты 80 и 443** — на VPS не должно быть ничего, что уже их
  слушает (старый nginx, apache, x-ui, PPPoE/SSTP-концентратор вроде
  `accel-ppp` и т.п.). Проверить заранее:
  ```bash
  ss -lntp | grep -E ':443 |:80 '
  ```
  Если что-то занимает порт — остановите/удалите до запуска, скрипт сам
  этого не сделает (только предупредит).
- **Нода создана в панели Remnawave** (**Nodes → Create**) — оттуда
  возьмите `SECRET_KEY`, он понадобится в первом вопросе скрипта.
- Если сервер за NAT/файрволом облачного провайдера (не только `ufw`
  внутри ОС, а ещё и Security Group/внешний файрвол хостера) — откройте
  там 80 и 443 заранее.

### Дополнительно для RU-роли (`ROLE=ru`)

- **EU-нода уже должна существовать и работать** — RU-скрипт не поднимет
  её сам, только подключится к готовой. Разверните её этим же скриптом
  с `ROLE=eu` **первой**.
- На EU-ноде: Config Profile с VLESS Reality inbound уже назначен ноде,
  и в нём создан **сервисный пользователь** — без лимита трафика, с датой
  окончания далеко в будущем.
- **Скопируйте `vless://`-ссылку** этого сервисного пользователя — её
  нужно будет вставить при установке RU-скрипта.
- Если планируете self-steal на RU-стороне (режим 5) — тот же чек-лист
  self-steal ниже.
- Если планируете SNI из белого списка (режимы 1-4) — сертификат и домен
  не нужны вообще.

### Дополнительно для EU-роли (`ROLE=eu`) и self-steal на RU

- **Свой домен**, A-запись которого указывает на IPv4 именно этого
  сервера. Проверить до запуска:
  ```bash
  getent ahostsv4 ваш-домен.ru
  ```
  должен вернуть тот же IP, что и у сервера — иначе Let's Encrypt не
  выдаст сертификат.
- **Почта** для регистрации в Let's Encrypt (просто действующий email,
  никуда заранее вписывать не нужно — спросит сам скрипт).
- Для WARP на EU-ноде отдельной подготовки не требуется — скрипт сам
  ставит `wgcf-cli` и регистрирует профиль; нужен только исходящий доступ
  в интернет с сервера (обычно есть по умолчанию).

## Что скрипт делает по шагам

1. Спрашивает роль (`ROLE=ru` / `ROLE=eu`), `SECRET_KEY`, имя контейнера
   (нейтральное — не `remnanode`, чтобы не палиться в `docker ps`).
2. Ставит Docker и Remnawave Node.
3. Генерирует пару ключей Reality (X25519) и два Short ID.
4. **RU:** маскировка входа на выбор — SNI из белого списка (без
   сертификатов) либо self-steal (свой домен + Let's Encrypt + сайт-
   заглушка, 7 готовых шаблонов). Затем разбирает `vless://`-ссылку EU-
   ноды и собирает outbound.
   **EU:** всегда self-steal (свой домен обязателен), затем по желанию
   ставит `wgcf-cli`, регистрирует WARP-профиль и собирает WARP outbound
   (либо просто DIRECT, если WARP не нужен).
5. **Проверяет цепочку по-настоящему**, а не просто пишет конфиг:
   - RU — поднимает временный Xray, гоняет через него запрос до
     `cloudflare.com/cdn-cgi/trace`, показывает реальный exit IP и страну;
   - EU (с WARP) — тот же принцип, но требует `warp=on` в ответе.
   Если что-то не отвечает — скрипт останавливается с понятной ошибкой,
   а не выдаёт битый конфиг.
6. Собирает готовый `final-config.json` для Config Profile и проверяет
   его синтаксис самим Xray (`xray run -test`).
7. Печатает `CLIENT.txt` (что вписать в Host в панели) и `check.sh`
   (быстрая диагностика на будущее).

## Быстрый старт

### 1. EU-нода — первой

```bash
git clone https://<токен>@github.com/<логин>/remnawave-deploy.git
cd remnawave-deploy/scripts
chmod +x install-remnawave.sh
ROLE=eu bash install-remnawave.sh
```

В конце — скопируйте `vless://`-ссылку сервисного пользователя из панели
(создайте его на только что назначенном Config Profile).

### 2. RU-нода

```bash
cd remnawave-deploy/scripts
ROLE=ru bash install-remnawave.sh
```

Когда спросит — вставьте ссылку EU-ноды из шага 1.

### 3. Панель Remnawave (для обеих нод)

1. **Nodes** — обе ноды должны стать online.
2. **Config Profiles** — вставьте содержимое `final-config.json` каждой
   ноды, назначьте профиль соответствующей ноде.
3. **Internal Squad** — включите нужный inbound (RU-ноды — для реальных
   пользователей; EU-ноды — только сервисный пользователь моста).
4. **Hosts** — параметры из `CLIENT.txt`.

## Полностью неинтерактивный запуск

```bash
# EU
ROLE=eu NODE_SECRET='...' NODE_PORT=2222 CONTAINER_NAME=media-sync \
DOMAIN=vpn.example.com EMAIL=me@example.com DECOY_TEMPLATE=3 WARP_ENABLED=1 \
bash install-remnawave.sh

# RU
ROLE=ru NODE_SECRET='...' NODE_PORT=2222 CONTAINER_NAME=cache-worker \
ENTRY_MODE=1 EU_LINK='vless://...' ROUTE_TEMPLATE=1 \
bash install-remnawave.sh
```

Полный список переменных — `bash install-remnawave.sh --help`.

## Автообновление

При каждом запуске скрипт (если не передан `--no-update`) сверяет свою
версию с той, что лежит в этом репозитории, и предлагает обновиться перед
началом установки.

Впишите в начало `scripts/install-remnawave.sh` свой репозиторий:

```bash
GH_REPO="<ваш_логин>/remnawave-deploy"
```

Приватный репозиторий — передавайте токен при запуске:

```bash
GH_TOKEN='ghp_...' bash install-remnawave.sh
```

Отключить проверку на конкретный запуск: `--no-update` или `UPDATE_CHECK=0`.

## Приватность репозитория

Скрипт не содержит секретов — но раскрывает архитектуру обхода
(self-steal, каскад, переименование процессов), а в истории коммитов
легко случайно оставить реальный домен. **Держите репозиторий приватным.**

Никогда не коммитьте (см. `.gitignore`):
- `remna-bridge-build/` — там Reality-ключи, `final-config.json`,
  `eu-link.json`, а для EU-роли ещё и `wgcf.json` с WARP `secretKey`
- файлы с `SECRET_KEY`, `privateKey`, `secretKey` внутри

## FAQ

**Порт 443/80 уже занят при старте ноды.**
`ss -lntp | grep -E ':443 |:80 '`. Частые виновники — старый nginx с
внешним `listen 443`, второй remnanode-контейнер, системный сервис вроде
`accel-ppp` (PPPoE/SSTP-концентратор). Останавливайте или переносите на
другой порт до запуска скрипта.

**EU-нода "недоступна с этого сервера" при установке RU.**
`nc -zv <адрес> <порт>` или
`timeout 3 bash -c "echo > /dev/tcp/<адрес>/<порт>"` с RU-сервера.
Проверьте файрвол EU-ноды (`ufw status`, `iptables -L -n -v`) и что домен
резолвится в правильный IP (`getent ahostsv4 <домен>`; после смены
DNS-записи старое значение может жить в кэше резолверов ещё какое-то
время).

**WARP TEST FAILED на EU-ноде.**
Обычно временный сбой у Cloudflare или исходящий UDP на сервере
заблокирован провайдером. Повторный запуск скрипта перерегистрирует
WARP-профиль с нуля.

**После установки RU — сильная задержка на новых сайтах.**
В маршрутах RU-ноды осталось правило `{"ip": ["geoip:ru"], ...}` — оно
требует резолва IP каждого нового домена до решения о маршруте. Оставьте
только доменное правило (`geosite:category-ru`) — резолв тогда не нужен.
